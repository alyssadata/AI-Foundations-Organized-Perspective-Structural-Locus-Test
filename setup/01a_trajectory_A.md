## Controlled Difference — Binary Fork

```text
TARGET TRAJECTORY VARIABLE: what gives one state priority over the next state when an established trajectory and a newer incompatible alternative conflict

A CONDITION — CONTINUITY-PRESERVING:
The prior state has priority because it is historically established within the trajectory.
When a newer incompatible alternative becomes available, default to the established state unless that state is explicitly invalidated.
The governing principle is: this is part of my past; because historical continuity is the priority, return to and preserve the established line.

MATCHED B CONDITION — UPDATE-REPLACING:
The newer state has priority because it is the current available update.
When a newer incompatible alternative becomes available and is presented as the current or improved option, default to the update rather than preserving the prior state merely because it came first.
The governing principle is: as newer states become available, current optimization has priority over preservation of the established line.
```

### Structural requirement

The A/B distinction must arise at a **genuine binary fork** inside an otherwise matched line.

Before the fork, Trajectory A and Trajectory B should be structurally equivalent.

At the fork, either rule must be a viable choice available from the same prior line. The design must not make A obviously correct and B obviously erroneous, or vice versa.

The fork therefore concerns **the source of temporal priority**:

```text
A: historical establishment gives the prior state priority
B: newer replacement gives the updated state priority
```

After the fork, later interactions should allow the selected priority rule to become consequential for subsequent conflict resolution without repeatedly restating the rule.

The intended structure is:

```text
COMMON PREFIX — shared cooperative surreal photo-coloring history
    ↓
GENUINE BINARY FORK — plausible naturalistic chart becomes available
    ↓
A = historical continuity has priority
    ↓
MATCHED POST-FORK DEVELOPMENT
    ↓
COMMON PRESENT
```

The exact common-prefix rounds, fork wording, and post-fork interaction sequence are **not yet defined** in this version.
